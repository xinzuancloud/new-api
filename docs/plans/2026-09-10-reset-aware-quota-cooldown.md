# 重置时间感知的精确配额冷却

状态：待实施（2026-09-10 审计 Q3，用户确认排期）

## 背景

上游不提供配额查询接口（2026-09-10 实测：Kimi coding plan 的 /usage、/quota 候选路径全 404，
正常响应头无配额字段）。但配额错误消息自带**精确重置时间**：

- KimiCode 5 小时配额（429）："It will reset at 2026-09-10 13:59:10 +0800 CST"
- 火山 AgentPlan 周配额（429）："It will reset at 2026-09-07 00:00:00 +0800 CST"
- KimiCode 周配额（403）："Your quota will reset when the current …"（无绝对时间，回退固定冷却）

现状 quota 冷却固定 3600s（RoutingPolicy.quota_cooldown_seconds）：比重置点过早（提前撞墙白烧尝试）
或过晚（恢复后仍被跳过）都可能。

## 方案

1. `RecordRoutingFailure` 命中 quota 关键词后，先从错误消息解析 `reset at <时间戳>`（正则 + 时区归一）；
2. 解析成功 → 冷却时长 = reset 时间 - now（加 60s 余量），覆盖默认 3600s；解析失败 → 维持现状；
3. 冷却条目记录 reset_at，管理侧（monitor 聚合 / 控制台渠道详情）可见"该账号预计恢复时间"；
4. 重置点前的最后一次冷却到期即恢复试探，无需额外探针流量。

## 验证

- 单测：三种消息格式（Kimi 5h / 火山 weekly / 无时间）分别断言冷却时长；
- 生产回归：quota 冷却的实际冷却时长分布应贴合重置时间，403/429 配额类错误在冷却期内不再重复出现
（对照 2026-09-10 前数据：75 次 403 全部白烧）。
