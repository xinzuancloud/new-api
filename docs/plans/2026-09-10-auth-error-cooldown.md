# 401/403/5xx 从"整渠道禁用/永不冷却"改为账号级短冷却

状态：待实施（2026-09-10 审计提出，用户已排期；5xx 部分经第 9 条确认并入）

## 问题

`RecordRoutingFailure`（service/routing_policy.go:45-58）只给两类错误冷却：quota 关键词命中（3600s）与 429（指数退避）。
其余错误游离在路由隔离之外：

- 401 命中 `ShouldDisableByStatusCode` → 走上游 auto-ban，**整渠道全局禁用**——单 key 渠道一个密钥事故，
  同账号所有模型、所有分组一起死，需人工重新启用。
- 403（非配额类，如账号被风控）→ 既不禁用也不冷却，永远留在候选池，每个请求白烧一次尝试。
- 5xx/断流 → 同样零冷却：坏账号在每个新请求上都会被重新首选（实证：SenseNova 旗舰 12 账号 24h 各背 ~130 次错误，
  均匀分布正是"无回避"的特征），26% 的请求要靠请求内重试救回。

生产实证（7 天）：401 零次（休眠风险）；403 共 75 次但全部能被 quota 关键词覆盖
（2026-09-10 已补配 "usage limit" 关键词），本改造针对的是**非配额类 403/401** 与 **5xx** 的兜底语义。

## 方向

- 401/403 → 账号级（account_resource 键）固定短冷却 5-10 分钟，成功请求清零；
- 5xx/网络错误/断流 → 账号级短冷却 30-60s（连续失败可小幅升档，封顶 5 分钟），成功清零；
- auto-ban 保留为最后手段（例如连续 N 个冷却周期内仍 401 才禁用）；
- 注意与 `processChannelError` 的 ctx 取消提前返回不冲突（取消时不记账的语义不变）。

## 附带小件（C4，同批次实施）

1. **冷却残留清除口**：渠道被手动重新启用/更新时，按 `channel:<id>`（及 account_resource 别名）删除本地与 Redis 冷却键
   （现状：冷却无任何外部清除点，管理员修好后最长还要等 3600s 才恢复选中）。
2. **坏 ModelMapping 告警**：`routingMappedModelName` 解析失败导致渠道被路由层排除时打 Warn 日志并带 channel id
   （现状：service/routing_policy.go:157-160 静默排除，零日志）。

## 验证

- 单测：模拟 401 → 渠道进冷却而非禁用；模拟持续 500 → 冷却期内不再被选中；恢复后成功请求清零冷却。
- 生产回归：观察自动禁用事件频率（当前渠道 44 因周配额被禁用属预期，不应回退该行为）；
  monitor 的 recovered/failed 比率应从 26%/2.6% 显著下降。
